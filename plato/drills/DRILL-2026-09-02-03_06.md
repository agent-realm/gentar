# d2-tweaker drill — bending the arena's portability knobs

## What I did (in character)

My laptop is not a clean CI runner and I made no apology for it. Two
gentar stacks side by side on this Mac (OrbStack), ports bent, project
renamed, scenarios and subjects mounted from /tmp, and a second checkout
wearing the first one's project name — because the knobs exist to be
bent, and the seams exist to be found.

Sequence (all from the drill worktree unless noted):

1. Preflight: docker context `orbstack`; ssh BatchMode to 10.10.10.52
   exit 0; ports 18133/14323/18134/14324 all free.
2. Stack A: `cp .env.example .env` + appended
   `GENTAR_CLICKHOUSE_HOST_PORT=18133` / `GENTAR_OTELCOL_HOST_PORT=14323`,
   `COMPOSE_PROJECT_NAME=plato-d2-stacka`, `GENTAR_BENCH_KEY_FILE`
   exported. `docker compose config` published 18133/14323 (r2's port
   check pattern, reused as my preflight). Build green; `smoke` exit 0
   (`smoke ok: Linux gentar-20260901-235803-937e7e ...`); spans in this
   stack's own ClickHouse. lsof: `127.0.0.1:18133 (LISTEN)` and
   `*:14323 (LISTEN)` — the loopback/all-interfaces split is as the
   compose comments claim.
3. GENTAR_SCENARIOS_DIR: scratch suite in /tmp/gentar-d2-tweaker/suites,
   run via the docs' exact pair (`-e GENTAR_SCENARIOS_DIR=/extra -v
   ...:/extra:ro`) — `tweaker-probe` exit 0. (Two stumbles on the way
   were mine, not the product's: `subject = "arena"` in a TOML names a
   /subjects subdir and fails with `local tar of /subjects/arena failed`
   — fair and actionable; and a `\;` inside a TOML basic string is a
   TOMLDecodeError — my quoting.)
4. GENTAR_SUBJECTS_DIR: exported at
   /tmp/gentar-d2-tweaker/subjects with a demo-subject/ payload; suite
   `tweaker-subject-probe` verified the payload inside the sandbox
   workspace. Exit 0.
5. Stack B side by side: same compose dir, `COMPOSE_PROJECT_NAME=
   plato-d2-stackb` + shell-exported ports 18134/14324 (shell beats
   .env for interpolation — verified via config). Build, up, binds
   green. Then finding 1: the follow-up `compose run` without the port
   exports fell back to the shared .env, recreated stack B's containers
   onto 18133, and died on the bind — taking stack B's live containers
   with it. Recovered with full exports; `otlp-selfreport` exit 0 on
   stack B, report gentar-20260902-000155-de099b.
6. Isolation, distinct names: stack B held exactly one scenario
   (otlp-selfreport, 1 run_id), stack A held smoke + both probes; each
   stack's ClickHouse returned 0 for the other's run_ids; stack A's
   otel_traces count 0, stack B's join returned the one run_id with
   agent_spans=1. Volumes separate.
7. Overlapping project name: a second checkout in /tmp with
   COMPOSE_PROJECT_NAME=plato-d2-stacka silently attached to the live
   stack A (finding 2) and its smoke run wrote spans into stack A's
   ClickHouse while its report went to its own out/.
8. `--env-file` split-brain probe (config only) — finding 3.
9. Teardown: `docker compose -p plato-d2-stacka down -v
   --remove-orphans` and same for stackb (0 containers, 0 volumes
   remaining under plato-d2*); bench-host `sbx ls` → "No sandboxes
   found"; /tmp scratch and the local .env removed. Six run reports
   remain in out/ (gitignored), one per compose run.

Known noise seen and waived per BLESSED.md: OrbStack `secrets 'uid',
'gid' and 'mode' are not supported` on every coordinator run.

## What the knobs proved

The per-knob story is honest: ports rebind exactly as named (and the
r2-steer 4318 anomaly stays unreproduced), scenarios and subjects mount
from anywhere the docs say, and two properly-named stacks on one host
share nothing — not volumes, not spans, not sandboxes. The seams are
all about IDENTITY and SCOPE: the port knobs live in a file while the
project knob lives in the shell, the project name is the only real
arena identity (ports are not), and the env-file that drives
interpolation is not the env-file the coordinator container reads.
Three findings, all in that family.
