# gentar v0.12.0

gentar's kit reads your suites the way the engine does, a run no longer changes the files of a
run it is queued behind, and a bench host can now carry several runner accounts safely: each
gets its own lock root, workspace root and builder workspace, and none can read or replace
another's. Suites that could not fail now can. `[verify] self_report` proves that telemetry
emitted inside a bench reached ClickHouse, with an example. Most of this comes from the
ground-up review of 2026-10-19 (findings A7, A8, B3, C4, GB2, SB03, SB05).

**Breaking:**
- The kit reads suites with a TOML parser. A suite is refused (exit 2) when its
  `[scenario] name` differs from its file name, when its file name holds anything but letters,
  digits, dot, dash and underscore, or when it writes `credentials` or `pass_env` as a string
  instead of a list.
- `gentar/run.sh --down` needs python 3.11+ or `tomli`, as every other mode already did.
- `GENTAR_CI_RUNNER` must carry a label of its own. A value made only of default runner labels,
  one naming the bench label, or one holding a backslash is refused before anything is
  scheduled.
- New scenario key `[verify] self_report`. A suite that sets it fails unless its span joins the
  run's harness spans; the dry-run reads it UNVERIFIED.
- Four kit files changed: re-copy `gentar/run.sh`, `gentar/plan.py`, `gentar/dryrun.py` and
  `.github/workflows/gentar-arena.yml` (the public variant too).

See "Upgrade, for adopters".

Already in v0.11.1, and listed here for adopters coming from v0.11.0: the pull request scan of
gentar's own CI (#104, #106, #107), `bin/sbx-file-login` on rootless Docker (#108), the sbx
secrets check in a clean environment (#102) and `verify-ref.sh`'s cleanup (#101).

## What changed, and why

### The kit reads a suite with a TOML parser (#96)

**Problem.** `gentar/run.sh` read scenarios with awk and grep, and its reading diverged from the
engine's. A deterministic step that printed `goal=1` made a suite judged, so a sweep skipped it
without the judge key. A comment mentioning triple quotes hid the `[scenario]` table, so its
subject and credentials went unread. `credentials = []` read as a credential never set (A7).

**Change.**
- `plan.py scenarios` reads every suite with `tomllib` (subject, judged by the engine's rule,
  credential groups, forwarded names), and `run.sh` asks it. A test holds that reading to the
  engine's on every scenario in the repo.
- A suite is its file name: a different `[scenario] name` broke the sweep and let
  `run.sh <name>` pass the pull request guard under a name with no file (GB2). It is refused, and
  so is a file name outside the allowed characters.
- `credentials` or `pass_env` as a string is refused, by the engine too, which read
  `credentials = "KEY_A"` as five one-letter names.

### A waiting run no longer changes a running one's files (#97)

**Problem.** `run.sh` fetched the engine and replaced `subjects/<subject>` before it took the
host lock, so a run queued behind another swapped both under the suites the other was still
running (B3, SB05). Two `bin/arena run` calls in one checkout shared a compose project, and the
second's teardown stopped the first.

**Change.** The kit takes the lock before its first write; `--stage-engine` and `--check` wait
for a running arena of the subject too. `bin/arena run`, `dashboard` and `ls` take a host lock
named after the compose project, and `bin/arena down` leaves a live run's arena alone.

### The bench runner's label is one variable (#98)

**Problem.** The kit refused a `GENTAR_CI_RUNNER` naming `arena`, the default bench label, but
not one naming a bench runner with another label, so pull request code could run on the bench
runner (C4). `["self-hosted", "linux"]` passed too, and every self-hosted runner carries those
labels (SB03). `runs-on` decodes JSON escapes, so `"arena"` passed a check of the raw text.

**Change.** The repository variable `GENTAR_BENCH_LABEL` (default `arena`) is the label the
bench job runs on. `plan.py` refuses a `GENTAR_CI_RUNNER` containing it or `arena`, one made
only of default labels, and one holding a backslash, and checks `GENTAR_BENCH_LABEL` itself on
every plan.

### Suites that could not fail (#99), and self-report proven (#99, #117)

**Problem.** `otlp-selfreport` checked only that the bench's OTLP drop file was non-empty, and
its span carried a timestamp ClickHouse read as 1970. `memhouse-house` and `memhouse-install`
accepted an HTTP error body holding a "3". `kommander-update` seeded nothing it could check
afterwards. A judged-policy test searched for a line that no longer existed (A8).

**Change.**
- New scenario key `[verify] self_report = true`: the coordinator relays the drop file before
  the verdict and fails the run unless the span joins the run's harness spans on `run_id` in
  ClickHouse within 30 s (assertion `otlp-join run_id`).
  [Example 10](../../examples/10-self-report/README.md) shows it in a shell-only suite.
- The engine's own suites above now fail when what they check is wrong.

### A bench host with several accounts (#112, #113, #114, #115, #116)

**Problem.** One host serving several repositories' runners, each under its own account,
shared paths in `/tmp` that any account could make first, read, or replace with a symlink: the
arena lock root, the local-mode workspace root that holds every bench's copy of the subject, and
the template builder's workspace. `bin/bench-host-provision` wrote every account's workspace
rule to one file, and a second account could get overlapping subordinate ids.

**Change.**
- **The lock follows the Docker daemon.** On rootless Docker each account has a daemon of its
  own, so its lock root is `/tmp/gentar-locks-<user>`, 0700, and one another account made first
  is refused (exit 2). On rootful Docker, or when `docker info` gives no clear answer, it stays
  the shared `/tmp/gentar-locks`. An explicit `GENTAR_LOCK_DIR` still wins.
- **The local-mode workspace root is the account's own.** A symlinked, foreign-owned,
  non-directory or relative `GENTAR_BENCH_WORKSPACE_ROOT` is refused (exit 2); a new one is made
  0700, and one of ours is kept at 0700. The default path is unchanged.
- **The template builder's workspace is the account's own**: per user by default, made 0700
  without `-p`, removed on exit, and refused if it is a symlink or another user's.
- A `GENTAR_BENCH_WORKSPACE_ROOT` or `GENTAR_TEMPLATE_WS` that ends in `/` or holds a `.` or
  `..` component is refused first: a test on `link/` reads through the link, and `rm -rf
  "link/"` removed the directory such a symlink pointed to.
- `bin/bench-host-provision` gives each account its own tmpfiles rule and the next free
  subordinate id range, and refuses ranges that overlap another account's.

### A dead holder's lock is reclaimed by one waiter only (#100, #118, #120)

**Problem.** On a host without `flock` (stock macOS), two waiters could both read a dead
holder's note; the second then removed the lock the first had just taken, and both ran.

**Change.**
- A reclaim takes a reap mutex, re-reads the note under it, and removes the lock only if the
  note is still the one judged dead, or, with no note, if the lock is still over a minute old.
  The same code in the kit's `run.sh` and in `bin/arena`.
- A lock root this user cannot write, and a stale lock or reap mutex it cannot remove, are
  named with exit 2 and the command to fix them, never waited on. Before, a waiter on such a
  root that held no lock yet waited forever.
- The `flock` path (Linux) never had the race and is unchanged.

## Upgrade, for adopters

1. Set `GENTAR_REF` to `v0.12.0`, or take the new kit's `run.sh`, and re-copy `gentar/run.sh`,
   `gentar/plan.py`, `gentar/dryrun.py` and `.github/workflows/gentar-arena.yml` (the public
   variant if your repository is public). `gentar/run.sh --check` then reports the kit files as
   current.
2. Check every suite: its `[scenario] name`, if set, equals its file name; its file name uses
   only letters, digits, dot, dash and underscore; `credentials` and `pass_env` are lists.
   `run.sh --check` lists every suite it would refuse.
3. Have python 3.11+, or `tomli`, wherever you run `run.sh --down`.
4. If your bench runner's label is not `arena`, set the repository variable
   `GENTAR_BENCH_LABEL` to it. Give `GENTAR_CI_RUNNER` a label the bench runner lacks.
5. On a bench host with more than one account, read the next section first.

## Hosts with more than one account

On a host where more than one account runs gentar, for example one runner
account per repository, each of those accounts needs its own copy of three
paths under `/tmp`: the bench workspace root, the arena lock root, and the
template builder's workspace. `/tmp` is writable by everyone, so a path that
one account creates there first can be read by the others, or taken over by
them. 0.12.0 refuses a path that is not the running account's own, and makes
new ones 0700. The defaults keep their old names, though, so on a host with
several accounts give each account its own paths, as below, before the first
run on 0.12.0.

### The bench workspace root (local mode)

In local mode (`GENTAR_BENCH_HOST=local`), each bench's workspace, and the
subject's code with it, lives under `GENTAR_BENCH_WORKSPACE_ROOT`. Its default,
`/tmp/gentar-workspaces`, is **shared**. Compose binds this root into the arena.

- `run.sh` and `bin/arena` now refuse, with exit 2, a root that:
  - is a symlink;
  - is not a directory;
  - belongs to another user;
  - is a relative path;
  - ends in `/`, or holds a `.` or `..` component.
- A new root is made 0700. An existing root of the account's own is set to 0700.
- **Give each runner its own root.** Use a directory the account owns, mode
  0700, made by its own tmpfiles rule:

      # /etc/tmpfiles.d/gentar-<user>.conf
      d /tmp/gentar-workspaces-<user> 0700 <user> <user> -

  Then set it in that runner's `.env`:

      GENTAR_BENCH_WORKSPACE_ROOT=/tmp/gentar-workspaces-<user>

  `bin/bench-host-provision` writes this rule for each account it sets up.
- Without that, the first account to run owns `/tmp/gentar-workspaces`, and
  every other account's local-mode run stops at the check with exit 2.
- A host whose rule already makes the root 0700 for its account passes
  unchanged.

### The arena lock root

- **On rootless Docker,** when `docker info` clearly reports rootless, each
  account has its own daemon, and its locks live in a private
  `/tmp/gentar-locks-<user>`, mode 0700. If another account created that
  directory first, the run is refused (exit 2). That is a denial of service,
  not a takeover. Claim the directory ahead of time with a tmpfiles rule:

      d /tmp/gentar-locks-<user> 0700 <user> <user> -

  Or set `GENTAR_LOCK_DIR` to a directory of the account's own; its locks
  then live in `$GENTAR_LOCK_DIR/gentar-locks`.
- **On rootful Docker, or when `docker info` gives no clear answer,** accounts
  may share one daemon, so they share the lock root `/tmp/gentar-locks`. Like
  the root made under an explicit `GENTAR_LOCK_DIR`, it is created world-writable
  (0777) and not sticky, on purpose: an account that finds a dead holder's lock
  must be able to reclaim it. The cost is that any local account can remove
  any lock in it. Point `GENTAR_LOCK_DIR` at a directory of the account's own,
  unless sharing with another account is what you want.
- **When the old shared `/tmp/gentar-locks` can go:** on a rootless host, only
  once every subject on that host runs 0.12.0 or sets `GENTAR_LOCK_DIR`, and
  no run is in flight. Older pins still use it by default. If a tmpfiles rule
  creates it, remove that rule too. On a rootful host it stays: it is the
  shared root.
- A run on an older pin and a run on 0.12.0 take their locks in different
  directories, so they do not exclude each other. Do not run one subject on
  both at once.

### The template builder's workspace

- `bench-template/build.sh` now builds in
  `${TMPDIR:-/tmp}/gentar-template-build-<user>`, not a shared
  `/tmp/gentar-template-build`. It refuses, with exit 2 and before any `sbx`
  call, a workspace that:
  - is a symlink;
  - belongs to another user;
  - ends in `/`, or holds a `.` or `..` component, which includes `.` and
    `..` themselves.
- It removes the workspace only if it was there at that check, and makes it
  0700 with `mkdir` without `-p`. It removes it on exit, failures included.
- A `/tmp/gentar-template-build` left by an older build is no longer used. Its
  owner removes it by hand.

### Explicit paths: what is not checked

- These checks look at the path itself, not at its parents. An explicit
  `GENTAR_BENCH_WORKSPACE_ROOT`, `GENTAR_TEMPLATE_WS` or `GENTAR_LOCK_DIR` must
  sit in a directory that only the account can write to, or in a sticky one
  such as `/tmp`. Two cases are not caught:
  - **A symlink in a parent component**, for example
    `/tmp/<link>/gentar-workspaces`: the root is made inside whatever the link
    points to, and whoever owns the link can repoint it later.
  - **A parent another account can write**: that account can rename or replace
    the directory after the check, and a `chmod` then follows whatever it put
    there.
- The defaults sit directly in `/tmp`, which is root-owned and sticky, so
  neither case applies to them. The builder's default sits in `$TMPDIR` when that is set,
  which is the account's own on most systems.

### Order, per host

1. For each account: write its tmpfiles rules (workspace root, and on rootless
   Docker the lock root), then run `systemd-tmpfiles --create` on that file
   only.
2. For each runner: set `GENTAR_BENCH_WORKSPACE_ROOT`, and `GENTAR_LOCK_DIR` if
   you use one, in its `.env`.
3. Re-pin each subject to v0.12.0 in its own pull request, re-copying the kit
   files.
4. When every subject on the host is on 0.12.0 and nothing is in flight,
   remove the old shared directories you no longer need, and their rules.

## Not live-proven

The mirror gate runs gentar's own bench suites on one host, as one account, with `flock`. What
this release changes outside that is proven by unit tests only:
- the lock root, the workspace root and the builder's workspace on a host with several accounts
  (each refusal and each 0700 path is tested on synthetic directories);
- the lock-reclaim fix, which needs a host without `flock` (tested on macOS, and on Linux with
  `flock` hidden from the `PATH`);
- `bench-template/build.sh`, which no gate suite runs;
- example 10, whose join is the one `otlp-selfreport` proves in the gate.

## Cleanup

- A `/tmp/gentar-template-build` left by an older template build is no longer used; its owner
  removes it.
- Remove the old shared `/tmp/gentar-locks` only once every subject on that host is on 0.12.0
  or sets `GENTAR_LOCK_DIR`: it stays in use on rootful Docker, when `docker info` gives no
  clear answer, and by older pins.

## Known limits

- On a rootless host, a run on an older pin and a run on 0.12.0 don't exclude each other: don't
  run one subject on both at once.
- A waiter on an older pin takes no reap mutex, so the lock-reclaim race stays open between it
  and one on 0.12.0 (hosts without `flock` only).
- Clearing a reap mutex left by a killed waiter is itself check-then-remove. It can misfire only
  after a waiter was killed inside the reap, with three more reaping within milliseconds.
- A lock holder whose note is never written, because it stalled for over a minute after taking
  the lock or because the write failed (a full disk), looks like a lock with no note and is taken
  for dead after a minute (hosts without `flock` only, as before).
- The shared lock roots are 0777 and not sticky by design, and the parents of an explicit path
  are not checked: see "Hosts with more than one account".
- No gate suite builds a template. Under rootless Docker, if the builder sandbox writes into its
  workspace as a uid that is not the account's, the exit cleanup leaves those files, and the next
  build stops at the ownership check or at `rm`. The first template build after the upgrade is
  the proof.
- The nightly skips subject suites when no subject token is set.
