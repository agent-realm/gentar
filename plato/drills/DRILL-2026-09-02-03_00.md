# d1-impatient — quickstart, literally, on the laptop

In character: build break, skimmed the quickstart block only, pasted it.

Beat 1 — literal quickstart. `cp .env.example .env` (no edits; defaults
already pointed at 10.10.10.52 + id_ed25519), exported the key file as the
block says, one `docker compose run --rm coordinator run smoke`. Exit 0
first try, report landed, quickstart SQL verbatim returned the smoke span
set. Goal ("one scenario's spans visible, reading as little as possible")
met in two commands. No hidden export, no context juggling, no key-path
trap bit: the only env the block names, GENTAR_BENCH_KEY_FILE, was exactly
enough on this Mac. That is the delight finding.

Beat 2 — the shadow. Curiosity probe of the published host port (the
compose file's own comment says it exists for host-side access):
127.0.0.1:8123 answered a foreign native ClickHouse (auth rejected),
deterministically, while `docker ps` claimed my container published that
very binding. Compose never errored — OrbStack silently coexists with the
native listener and the arena's publish loses. The quickstart itself is
immune (its SQL runs through `docker compose exec`, compose-internal), so
the five-minute user never learns anything is wrong; only host-side
consumers read the wrong server. Applied the obvious fast fix (knobs are
greppable in .env.example in seconds: 18132/14322), down + rerun, second
smoke PASS, and 127.0.0.1:18132 now answers the arena (6 spans). Fix
works; you just have to already know you need it.

Known noise seen and ignored: OrbStack `secrets 'uid', 'gid' and 'mode'
are not supported` warning (waived at the s2 gate).

Bench-host: both of my runs' sandboxes were destroyed by the suites
themselves (sandbox name = run id: gentar-20260901-235645-e504eb,
gentar-20260901-235850-06c1ff — neither in `sbx ls` after teardown). Two
foreign `gentar-` sandboxes from concurrent actors were live at teardown
(gentar-20260901-235925-216868, gentar-20260901-235951-ceb023) —
recorded verbatim, untouched.
