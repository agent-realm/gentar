Gentar Scope Map

What contains what, and how many of each. The system spans three machines, two lifetimes and two integration modes. Most confusion comes from mixing the lifetimes up — or from reading a cardinality that only holds in one mode as if it held in both.

A SUBJECT REPO NEED NOT CONTAIN A gentar/ DIRECTORY

In central mode it contains no arena config at all — its scenarios are contributed to the arena repo by PR, and its checkout is cloned into subjects/ at run time. Where a claim below holds for only one mode, it says so.

02What happens on one push

The same six stations run whether you type gentar/run.sh locally or push to main. Only station 2 differs — locally, you are the dispatcher.

The loop back to station 4 is dashed because it is conditional, and this is the detail most worth getting right.

THE MATRIX DOES NOT BUY PARALLELISM ON ITS OWN

All six gate jobs request the same [self-hosted, gentar-bench] label, so with one runner they queue and run one after another. On top of that, gentar.yml sets concurrency: gentar-<ref> with cancel-in-progress — deliberately, because the bench-host is a single VM and two compose stacks spawning sandboxes there would race on names.

04The one edge that limits you

WHY THE COLLAPSE MATTERS

Today they are deliberately the same VM, and the header comment in gentar.yml says so: Docker, sbx and the compose stack in one place, with the coordinator SSHing to itself. For a single-arena setup that is the right call. The roles still size differently: a runner is a tiny polling process that holds GENTAR_BENCH_KEY and needs GitHub reach; a bench-host is a heavy box that needs nested KVM and runs untrusted agent code. Buying one more CI lane by cloning a heavy nested-virt machine is the wrong trade — and it would not buy any more benches anyway.

TWO THINGS WORTH CHECKING AGAINST ANY BENCH-HOST

cpu=host is mandatory on a virtualised bench-host. An sbx sandbox has its own kernel, so nested virt is required. Confirm /dev/kvm exists inside the guest before believing a bench-host works — the failure is otherwise silent until the first sbx create.

Bench teardown is best-effort by design, so leftovers are possible. BenchHost.rm() never raises — a failed teardown must not mask the real verdict — and the CI teardown step only reports what is left. A crashed or cancelled run can leave a sandbox and its /tmp/gentar-workspaces/<run-id> behind; one was observed on 2026-08-18. "The container is the reset" is a contract about the next run getting a fresh bench, not a guarantee that the previous one was reaped. Confirmed, and fixed in 0.1.0: the arena side of this gap put the pilot’s machine under — compose run --rm removed only the coordinator while clickhouse and otelcol survived via depends_on, stranding two containers and a named volume per project. bin/arena now starts every service as a one-off compose run -d --rm, the only way to get daemon-level AutoRemove, so a stopped arena container is removed by the daemon itself even when a SIGKILL prevents any trap from running. The bench side of the finding stands as written: a bench is still reaped best-effort, by design.
